# 개발 워크플로

이 프로젝트의 작업 절차. 1인 개발 규모에 맞게 단순하게 유지한다.

## 기능 개발 파이프라인

```
설계 판정 → 구현 → 검증 → 문서화 → 커밋
```

1. **설계 판정**: 새 기능·이상현상·연출은 [design-principles.md](./design-principles.md)를
   먼저 통과시킨다. 충돌하면 구현 전에 버린다. 이론적 타당성은
   [game-design-theory.md](./game-design-theory.md)(시스템)·[fear-cognition.md](./fear-cognition.md)(공포 연출)의
   체크리스트로 검증한다.
2. **구현**: 콘텐츠는 `src/data/` JSON으로, 로직은 `src/systems/`로.
   이상현상 추가에 코드 수정이 필요해지면 멈추고 스키마부터 고친다.
3. **검증**: `npm run dev`로 해당 밤/구간을 직접 플레이. 시각 변경은 데스크톱+모바일
   뷰포트 둘 다 확인. 성능 예산([development.md](./development.md)) 초과 여부 확인.
   코드가 바뀌었으면 `npm run build:local`로 `play-local.html`도 재생성 (더블클릭 테스트 파일 동기화).
4. **문서화**: 코드와 **같은 커밋**에서 관련 문서 갱신 —
   시스템 변경 → game.md, 이상현상 추가 → anomalies.md, 구조 변경 → development.md,
   서드파티 추가 → licenses.md (즉시), 방향 결정 → game.md '결정 기록'.
5. **커밋**: Conventional Commits + 한국어 본문. 예: `feat: 접힘 reveal 자막 연출 추가`

## 콘텐츠 추가 절차

**먼저 [stages.md](./stages.md) §1에서 공통인지 스테이지(=밤)별인지 정한다.**
스테이지별이면 반드시 데이터로 표현할 수 있어야 한다 — 밤 추가에 코드 수정이 필요하면 설계 실패.

이상현상:
1. anomalies.md 목록에 행 추가 (ID, 분류, 정상→이상)
2. 명확성 자가 테스트: "스크린샷 두 장을 나란히 보여주면 3초 안에 찾는가?"
3. anomalies.json에 데이터 추가 (`night` = 등장 시작 밤) → 플레이 확인 → 커밋
4. **stages.md §2 현황판 갱신** (그 밤에 무엇이 늘었는지)

## 플레이테스트 규칙

- 밤 하나가 완성될 때마다 **직접 처음부터** 플레이 (개발자 시점 스킵 금지)
- 외부 테스터에게는 조작법만 알려주고 규칙은 알려주지 않는다
  (무설명 학습이 되는지가 이 장르의 핵심 품질)
- 기록할 것: 오판 지점, 리셋 후 이탈 여부, 이상현상별 발견 시간, 웃은 지점

## 릴리즈 절차

1. 버전 태그 (v0.x) + CHANGELOG 갱신
2. main 푸시 — **pre-push 훅이 `npm run deploy`(빌드 → gh-pages 브랜치)를 자동 실행** →
   라이브 URL 직접 플레이 (캐시 무시 새로고침)
   - 훅 설정(클론마다 1회): `git config core.hooksPath .githooks`
   - 배포 없이 푸시만: `SKIP_DEPLOY=1 git push`
3. 모바일 실기기 1회 확인

## 작업 성향과 그에 맞춘 규칙 (2026-08-03 세션에서 도출)

한 세션(컨셉 확정 ~ 퇴근길 튜토리얼 완성)을 돌아보고, **이 개발자의 실제 작업 방식**에서
반복적으로 효과가 있었던 것과 비용이 컸던 것을 규칙으로 남긴다.

### 살릴 것 — 검증된 강점

- **공간 정합성 감각이 정확하다.** 실플레이 중 나온 지적이 전부 실제 결함이었다:
  뒤돌아보니 있으면 안 되는 건물 / 차가 다음 구간까지 따라옴 / 신호등이 둘 다 같은 쪽을 봄 /
  되돌아가면 암흑 막다른 끝 / 벽 마감이 상자 같음.
  → **규칙**: 신규 공간 요소는 "**뒤돌아보기·구간 넘기기·되돌아가기**" 세 동작을 반드시 통과시킨다.
  자동 검증으로는 잘 안 걸리고, 이 눈으로는 한 번에 걸린다.
- **연출 제안이 설계 원칙과 자연스럽게 맞물린다.** 다리 밑 터널(순간이동 대체), 신호등과 차,
  180° 돌려세우기 — 전부 "UI가 아니라 세계로 말하기"였고, 무설명 학습(§0)·정물성(§1)과 충돌하지 않았다.
  → **규칙**: 막고 싶을 때 **벽을 세우기 전에 연출을 먼저 찾는다.** 보이지 않는 벽은 최후수단.
- **문장을 짧게 자르는 감각.** "차에 치인 것 같은 꿈을 꾼 것 같다", "이건 못 참지" —
  길게 설명하면 사고가 되고 짧게 흐리면 꿈이 된다.
  → **규칙**: 자막은 2줄 이내. 정보를 늘리는 대신 **위치를 나눠** 걸음이 문장을 끌게 한다.

### 조심할 것 — 이 세션에서 비용이 컸던 패턴

- **재설계가 픽션 레이어에만 집중되는 경향.** 하루에 컨셉이 다섯 번 바뀌었지만
  (감자튀김 → 약 FF-1204 → 감자튀김 회귀 → 귀갓길 중심 → 괴담 2축),
  그동안 **상호작용은 "W를 누르고 있다가 가까이서 한 번 클릭"으로 내내 같았다.**
  "재미가 없다"의 원인이 여기 있었다 — 세계관을 아무리 바꿔도 손끝 감각이 안 바뀐다.
  → **규칙**: 컨셉·서사를 바꾸기 전에 먼저 묻는다. **"이 변경이 플레이어의 동사를 바꾸는가?"**
  동사가 그대로면 재미도 그대로다. 동사를 바꾸는 변경(신호등·차처럼 기다림에 값을 매기는 것)이
  픽션 교체보다 우선순위가 높다.
- **직접 플레이 검증이 계속 뒤로 밀린다.** 기획·이론 문서는 2400줄인데
  처음부터 끝까지 플레이는 아직 한 번도 없다. 재미 판단에 필요한 정보가 여기서만 나온다.
  → **규칙**: 구간 하나가 바뀌면 **그 구간만이라도 직접 걷는다.** 헤드리스 검증은
  "동작하는가"를 답하지 "재밌는가"는 답하지 못한다.

### 협업 방식 (확인된 선호)

- **확인 질문 대신 결정 후 보고.** 선택지를 늘어놓지 말고 판단해서 진행하고, 근거와 대가를 함께 말한다.
  되돌리기 어려운 것(배포·삭제·이름 변경)만 먼저 확인한다.
- **작은 왕복.** 큰 배치보다 한 번에 하나씩 보고 고치는 리듬을 선호한다.
- **근거는 실측으로.** "될 것 같다"가 아니라 "이 값이 나왔다" — 스크린샷·수치·좌표를 함께 낸다.
  임계값(응시 각도·신호 주기·속도)은 **가정으로 적지 않고 실측으로 잡는다**
  (avert 임계는 2회, 신호등 주기는 1회 교정 후 확정됐다).
